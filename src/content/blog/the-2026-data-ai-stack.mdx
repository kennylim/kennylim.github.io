Every claim below carries a bracketed reference, verified against primary sources this month.*

## The position in one paragraph

Build a company around **context and the closed loop**; rent the substrate, which in 2026 finally consolidated into interoperable parts. Own the governed knowledge your agents consume and the workflow your agents complete — the two things no vendor roadmap contains. Everything else is integration. The YC 2026 signal is blunt: AI is the default substrate, and what wins is *owning full workflow loops*, mostly in infrastructure and regulated, real-world domains [1][2].

## Reference architecture: one stack, two planes

<StartupStackDiagram caption="Figure 1 — the reference stack, tinted by what a small team should build (left rail) versus rent." />

The stack answers two clocks at once. **The log serves *now*** — agents, features, and context that must be fresh within milliseconds. **The table serves *always*** — truth, metrics, models, evals, and the audit trail. Reprocessing lives at both: replay the log for the hot path, recompute the table for the archive. The Kappa architecture (Kreps, 2014: one stream, reprocess by replay [3][4]) is finally practical at the hot path because Rust streaming databases disaggregated their state onto S3 — but replay is still physics, so a batch-reconcilable lake remains the source of truth [5][6][7].

<TwoPlaneDiagram caption="Figure 2 — the two planes. Fresh by the log, checked by the table, one schema contract between them." />

**Rule of thumb:** anything an agent reads or writes in its loop lives on the log plane *and* lands in the table plane within contract SLA. One schema, two velocities.

## Deciding the storage layer

The format wars are over; the niches remain. **Apache Iceberg (v3) is the default** table plane: engine-neutral, REST-catalog governed, v3 adding deletion vectors, row lineage (cheap CDC out of the lake itself), VARIANT for semistructured, and native implementations like iceberg-rust feeding the streaming plane [8][9][10]. Delta is the polished answer *inside* Databricks; Paimon the streaming-first (Flink/LSM) lake format; Hudi the upsert specialist [11][12]. For AI payloads, **Lance** (Rust, columnar-random, vector-native) and emerging formats like Vortex are a different class — file formats with their own dataset versioning, stored beside Iceberg-managed tables, not instead of them [13][14].

**The honest exception — DuckLake.** Introduced May 2025 by the DuckDB team, it keeps Parquet files and moves *all* metadata into a plain SQL database (Postgres/SQLite/DuckDB), yielding ACID, MVCC and time travel with no metastore, no compaction service, no catalog operation [15][16][17]. With **Quack** (May 2026, DuckDB 1.5) — an HTTP client-server protocol with concurrent writers, already reimplemented in pure Rust with federated Iceberg joins — a five-person company can run *the whole table plane on one binary* [18][19][20][21]. Recommendation: **start DuckLake if you have one engine and fewer than ten humans; adopt Iceberg the day a second engine or a regulator shows up.** DuckDB's support matrix (Iceberg, Delta, Lance, DuckLake first-class) makes that migration a query, not a project [22].

**Catalog:** run an open REST catalog — Lakekeeper or Polaris for neutrality; Unity Catalog if Databricks-centric (its 2026 interoperability expansion made managed tables readable externally) [23][24][25]. The catalog is where governance, sharing and (increasingly) agent permissions will concentrate — plan for it to be your center of gravity [26].

## Deciding ETL — from streaming ingestion to contract-enforced transformation

Four moves, and the interesting one is in the middle: how transformations *learn* that new data has arrived.

1. **Zero-ETL first.** Operational Postgres on the lake substrate (Lakebase-style) means app data needs no pipeline [27][28]; SaaS/databases stream in via Fivetran, now merged with dbt Labs (~$600M combined, positioned explicitly as "data infrastructure for trusted AI agents") [29][30]; event streams land natively as Iceberg (Kafka ecosystem, Confluent's BYOC WarpStream, now part of IBM's $11B platform) [31][32].
2. **Land raw, append-only, at the schema you agreed on.** The raw/bronze layer is Iceberg appends of what the source *is* — no casts, no opinions, replayable forever (v3 row lineage makes even this layer auditable [8][9][10]). The contract is enforced at the bus before anything touches storage [86][87].
3. **Trigger on arrival, not on cron.** The proven patterns, in order of how little you should have to build:

| Trigger pattern | How it works | Reach for it when |
|---|---|---|
| Native sync→transform | Fivetran "integrated scheduling" fires the dbt Cloud job at the end of every sync — the connector itself decides when dbt runs [73][74] | dbt Cloud + Fivetran; the zero-plumbing default |
| Webhook → event → run | Source posts "sync complete"/commit events to an event bus; a listener executes the right dbt selection — Prefect webhooks, Airflow 3.0 event-triggered DAGs [75][76] | Mixed sources, self-hosted dbt, sub-minute latency |
| Asset/data-dependency scheduling | Airflow 3 *assets* and Dagster *assets* treat each dbt model as a versioned thing; upstream materialization auto-fans-out to downstream runs — or Cosmos compiles the dbt DAG straight into Airflow [77][78][79][80] | Multi-team DAGs where lineage should be the schedule |
| Freshness as a first-class signal | dbt `source-freshness` gates and Dagster's update-checking assets ensure you never spend compute on an empty interval [79][80] | Volatile sources; avoid firing at empty intervals |
| SQLMesh signals | The scheduler advances an interval only when a user-defined signal says that interval's data is ready — file exists, row count stable, commit visible [81] | Near-real-time microbatch without inventing your own sensors |
| Streaming microbatch | Databricks-style `AVAILABLE_NOW` micro-triggers turn bronze→silver merges into a standing stream job — SQLMesh/dbt models run on the same cadence [83] | The Kappa plane; minutes-to-seconds freshness |

Mechanically: **dbt microbatch/incremental models with MERGE over the CDC envelope** (op, ts, before/after) — the pattern dbt's own near-real-time guidance documents [84] — or **SQLMesh `INCREMENTAL_BY_UNIQUE_KEY`/`SCD_TYPE_2` kinds** applied to the same envelopes, whose virtual-data-environment plans make the change-apply loop CI-gated rather than hope-based [82]. The raw-to-target write is the same either way: an idempotent merge keyed on (PK, commit-LSN), so replays converge instead of double-count.

<StreamingPipelineDiagram caption="Figure 3 — streaming ingestion to serving: two planes meet here; the numbered gates are where data contracts bind." />

4. **Stream the hot path** through the Kappa plane — RisingWave-style Rust streaming databases now pitch themselves as replacing Debezium+Kafka+Flink+a serving DB with one system, incremental materialized views with state on S3; Apache Fluss extends the log-native option into incubating reality [5][6][35][36].

**How contracts are enforced — three gates, one file.** The literature has converged on defense in depth [87][88][89]: **① at the bus** — Confluent-style schema registry rejects incompatible producers at write time (compatibility modes + JSONata/CEL quality rules + PII tags) [86]; **② at the model** — dbt model contracts fail the build when a SELECT drifts from the declared schema (typed columns + constraints, hardened for Iceberg/Delta); SQLMesh audits run in the plan diff [85][82]; **③ at the product edge** — the same contract rendered as docs + SLAs + freshness monitors (DAG-style DUAs), consumed by agents as well as humans. Keep the **ODCS YAML in git as the single source**, generate registry subjects, dbt contracts and catalog policies from it in CI (`datacontract-cli`, buf) — enforcement stops being a meeting [88][89][33][34]. Breaking changes travel as versioned proposals with migration windows, never as surprises at 3 a.m. [90][91]

## Deciding state, memory, and the OLTP question

Every agent needs a database it can trust, branch, and forget. The validated pattern is **Neon/Lakebase-style Postgres**: ephemeral stateless computes, quorum-replicated WAL safekeepers, pageservers reconstructing LSN-indexed history on object storage — Git-like copy-on-write branching and scale-to-zero as consequences, not features [37][38][39][40]. Aurora proved the split; Neon finished it; DSQL generalizes it to distributed [41][42].

**Guardrails, from the audit:** WAL-before-ack adds tail latency; autosuspend cold-starts sting chatty agent loops; **branches nobody prunes are the new table sprawl**; and Postgres-as-working-memory must not become the archive — logs compact, branches expire, only the lake remembers. Beside it, a funded **agent memory layer** — Mem0 ($24M Oct 2025), Letta (MemGPT), Zep/Graphiti temporal graphs — for durable, forgetting-aware state between the context window and the row [43][44].

## Deciding the ML lifecycle: retrieval-first, fine-tune second, train almost never

- **Retrieval before weights.** Production RAG in 2026 is retrieval *engineering*: hybrid BM25+dense with RRF fusion, cross-encoder or listwise rerankers (Cohere Rerank, bge, Jina), late-interaction (ColBERT/ColPali) for documents and screenshots, contextual retrieval at index time, GraphRAG where answers are joins [45][46][47][48][49]. Long context didn't kill RAG — it repriced being wrong.
- **The model layer is settled enough to shop.** For agentic/tool work, evaluate on the **Berkeley Function-Calling Leaderboard v4** plus your own trace evals: the open-weight field (Qwen3.8, DeepSeek V4 under MIT, GLM-5.x, gpt-oss-120b) matches proprietary on standard tool tasks, so pick by license, cost and serving fit [50][51][52][53].
- **Fine-tuning is the training.** LoRA-style jobs on Modal/RunPod or hosted at Together/Fireworks; the inference layer repriced to reported $15–26B valuations this September because *running* models became the business — treat that as a cost warning, not a tailwind [54][55][56].
- **Serving**: vLLM/SGLang with tool-call parsing and guided structured output — agents eat schemas [57]. **Features**: Feast if self-hosted, Tecton-in-Databricks if you bought the platform (its acquisition was explicitly about agent-latency context) [58]. **The loop**: MLflow/W&B registries, **evals in CI** (RAGAS goldensets + Langfuse/Braintrust traces) as release gates — the unit tests of this era [49][59].

## Deciding agents, interfaces, BI and data products

Protocols are neutral now; act accordingly. **MCP** — governed by the Linux Foundation's Agentic AI Foundation (Dec 2025) with A2A (Google; IBM's ACP merged in) alongside it since Aug 2026 — is the tool plane; adopt it as your product's API surface for agents, and use A2A only for cross-org delegation [60][61][62][63]. **Agent Skills (SKILL.md)**, open since Dec 2025 and implemented across 40+ platforms, is where your runbooks, review checklists and dbt style guides become executable knowledge — write them in version control like code [64][65][66].

BI is conversational/agentic — Databricks Genie ("Genie One" + ontology at DAIS 2026), Snowflake Cortex Analyst/Intelligence, ThoughtSpot Spotter, Tableau — and all of it succeeds or fails on the **semantic layer**, which is standardizing as Apache Ossie/OSI (Snowflake, Databricks, dbt and 50+ orgs) [67][68][69][70]. Ship governed metrics there; the dashboards, the text-to-SQL and your own agent products then read the same definitions. One context, many consumers.

## The operating plan — 30 / 90 / 365 days

**Day 30.** One vertical workflow, one model behind one interface. Postgres with branching, pgvector, one DuckLake (or Iceberg) table, Temporal for the loop, MCP server exposing your product's verbs, Langfuse traces on every call. Demo = the loop closes, not a chatbot.

**Day 90.** Hybrid+rerank retrieval over the domain corpus; the SKILL.md library encoding your operators' procedures; contracts in CI; Kappa plane feeding agent context sub-second; eval gates blocking deploys; semantic metrics published in Ossie-compatible form.

**Day 365.** Fine-tune *only* where traces prove retrieval+prompt plateau; migrate ingest to zero-ETL as volume justifies; publish governed context so third-party agents can consume you through MCP/A2A — the network-effect position. Re-audit the stack each quarter: this field moves on acquisition quarters, not conference years.

## What would change my mind

Honest failure modes, carried from the audit: an Iceberg-v3 + DuckLake convergence that ends the "when to adopt" argument early; a security incident class in MCP supply chains that forces closed tool planes (2026 already logged server CVEs — assume data is hostile until proven otherwise) [72]; agent-identity/quota/blast-radius governance maturing at the catalog layer and commoditizing the tool plane; or long-context + caching economics inverting the retrieval-first rule. None are visible enough today to build against — but any one flips a row of the table above, which is why the table cites sources instead of vibes.

## Final recommendation

If you asked me on Monday, with five engineers and a vertical to conquer: **Iceberg v3 on a REST catalog, DuckLake while small; Postgres-with-branches as the agent's working memory; the lake as the archive; a Rust streaming DB on the hot path; zero-ETL and contracts instead of pipelines-and-hopes; retrieval before fine-tunes before training; vLLM or one inference platform, never both until forced; MCP as your API surface, SKILL.md as your institutional memory, Ossie-format metrics as your semantics; evals in CI as your release process.** Own the context. Close the loop. Keep one copy of the truth on two clocks.

That is the stack. The rest is execution.
